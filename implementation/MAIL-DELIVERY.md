# 科学の案内メール：実装と接続条件

2026-09-14。今回の採択は、メール＋確認コード、任意の配信同意、初回2通・週替わり・希望分野の公開通知、受験状況と興味による出し分け。旧 `docs/stepmail-loop-v1.md` の毎日7通・腕試し10問・架空の紹介文は現行配信に使わない。

## 実装済み

- 登録直後と3日後の2通は `science` 同意の初回取得時だけ予約。週替わりは `weekly` 同意を持つ確認済み利用者へ、現在公開中の週について1件だけ予約する。500人ずつ継続でき、重複実行で再予約しない。
- 初回案内は、中断中なら保存した受験へ、受験済みなら次の受験へ、興味分野があればその分野20問へ案内する。固定した「昨日受けたはず」などの文面は使わない。
- 今週の10問を完了した人、受付期間を過ぎた週、30日以上前の初回案内は送信対象から外す。キューに入った後も、送信直前に同意・受験完了・確認済みアドレスの変更を調べる。
- 1人について同時に1通だけ処理し、受け付け済みの配信から24時間あける。停止済みの同意を勝手に再取得しない。テーマごとの解除はマイページ、メール内の停止リンクは科学検定の案内3テーマをすべて解除する。アカウントと受験権は維持する。
- 停止リンクは利用者別の推測困難な値とし、DBにはハッシュを保存。GETは確認画面だけ。POSTはログイン・Cookieに依存せず、本人のメール内トークンで停止する。メールアプリ向けの `List-Unsubscribe` / `List-Unsubscribe-Post` も出力する。
- SMTPはNodemailer 10を使用し、465のTLSまたは587の必須STARTTLS、証明書検証有効。外部URL・ファイルをメール内容として読ませず、ニックネーム等はHTMLエスケープする。送信先を1件に限定し、本文のハッシュ・安定したMessage-ID・処理状態を保存する。
- SMTPが一時的な拒否を明示したときだけ、15分・60分の待機を経て最大3回まで試す。タイムアウト・接続切断など受付結果が不明な場合は `blocked / delivery_outcome_unknown` とし、自動再送しない。処理が中断しても、送信前の中断と送信許可後の不明な結果を区別する。
- `/api/science-jobs/mail` は32文字以上の `CRON_SECRET` を要求。1回の実行で最大1通をSMTPへ渡し、短いバッチで継続する。メールアドレス・本文・SMTP資格情報をジョブのJSON応答やエラーログへ出さない。

## 設定と公開条件

`science_config.release.mailDelivery` と `newAttempts` の両方が有効で、下記の設定が完全なときだけ配送する。現時点では未設定・配信無効。Supabase Authの確認コード送信は別のSMTP設定であり、アプリ側の設定だけではOTPは開通しない。

| 設定 | 用途 |
|---|---|
| `SCIENCE_MAIL_ORIGIN` | 所有するHTTPSの公開オリジン。パス・クエリ・認証情報なし |
| `SCIENCE_MAIL_FROM` | 送信サービス側で利用を確認した差出人アドレス |
| `SCIENCE_MAIL_FOOTER` | 正式な運営者表示・所在地等を確認したフッター全文 |
| `SCIENCE_MAIL_UNSUBSCRIBE_SECRET` | サーバー専用の十分に長いランダムな秘密 |
| `SCIENCE_SMTP_HOST/PORT/USER/PASSWORD` | 許可された送信サービスのSMTP接続。秘密をGit・チャットへ書かない |
| `CRON_SECRET` | 配信ワーカーの認証。日次集計と共用するエンドポイントのBearer値 |

送信サービス・差出人の認証・フッターを確定し、許可されたテスト受信者でOTP、HTML/テキスト、返信先、停止、迷惑メール判定を確認してから有効化する。RFC 8058のメールアプリ内解除には、送信サービスが解除関連ヘッダーを含めてDKIM署名することも必要。アプリでヘッダーを作っただけで、その受信側対応まで検証済みとはしない。

スケジュールは未設定。1回1通の処理を十分な頻度で起動できるワーカー・配信サービスが必要で、Vercel Hobbyの日次実行だけで大量の即時配信ができるとは扱わない。既存のMyASPを主配信系に選ぶ場合は、現在同意のCSVだけでなく配信停止の同期を接続し、SMTPワーカーとの二重配信を避ける。

## 運用上の残り

- `accepted` はSMTPサービスが受け付けた状態。受信箱への到達や開封の実績ではない。バウンス・苦情の通知連携は、送信サービスの決定後に接続する。
- 不明な送信結果はMessage-IDと時刻でサービス側のログを確認する。ログなしで `pending` に戻さない。管理画面の停止件数とジョブ履歴には現れるが、送信結果の照合専用UIは未実装。
- 希望分野の長い本試験は未公開。`domain_opening` の同意は保存するが、公開していない受験の案内は作らない。実際の公開イベントと通知テンプレートを接続する段階が残る。
- 勉強会・専門家紹介・理系とーくバー等の企画メールは、実在する企画・日時・対象を確定してから原稿を登録する。架空の予定や自動作成の告知を送らない。
- 送信直前の確認とSMTPへの引き渡しは、異なるサービス間の操作。引き渡し後の配信を取り消したり、全サービスをまたぐ厳密な一回配送を保証するものではない。受付不明時に自動再送しない方針で重複を抑える。
