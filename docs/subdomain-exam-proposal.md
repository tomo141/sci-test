## 2. スコアレンジ（確定）

現行コードの分野スコアは実は **1–99**（`scoringConfig.domainMinScore=1 / domainMaxScore=99`, `internalToDomainScore`）で、総合スコアが **10–990** です。依頼文の「0–990」と現行分野スコアのスケールが一致しないことを確認した上で、

**→ 小分野スコアは総合スコアと同じ 10–990 スケールで表示することに確定。**（分野スコアの1–99とは別スケールになる。内部推定値は総合・分野と同じ内部レンジ10–990を使い、`internalToDomainScore` 相当の変換は小分野には適用しない＝内部値をほぼそのまま表示レンジにマップする）

## 6. プール不足時の出題・公開ロジック（確定）

- **出題**: 対象小分野の問題数が20問未満でもサイクル内で**重複を許して出題**する（同一問題の再出を許容し、20問を埋める）。プール数に応じた選択不可のゲートは設けない。
- **公開**: コード・DB・UIは**全100小分野を最初からフル実装**する。ただし小分野選択UIでの表示・非表示は**公開フラグ**（例: `subdomainReleaseStatus` のような設定。DBテーブル管理でも定数管理でも良いが、後から作問が進んだ小分野を随時反映できる仕組みにする）で制御し、運用側がプール充足を見ながら小分野ごとに公開していく。
- **過去回答履歴**: 旧subdomainラベル付きの既存 `answers` / `proficiency_estimates` は**遡及的に新小分野へ変換しない**。小分野スコアの集計は**リリース後の新規回答のみ**を対象に開始する（総合・分野スコアの既存集計には一切影響させない）。
